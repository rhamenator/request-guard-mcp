# v0.1.5 published container qualification

This bounded run tested the **published** experimental v0.1.5 GHCR image on
2026-10-21, not a local rebuild. Request Guard classifies inbound metadata
provided to its MCP tools; running it in a container does not intercept other
agent traffic.

## Artifact and configuration

- Source tag: `v0.1.5` at `f76ff9d2558fac705f091d9b858d3bc180b4f0bd`.
- Pulled `ghcr.io/rhamenator/request-guard-mcp@sha256:0fd3f54fc331ab3ef9b0be45a7fc97a459038ebad1b37ebc68dec482b1eee597`.
- The index contained linux/amd64 manifest `sha256:2ffde1470483a7f29112d985ef5e3317198dc0b2921bd9d4b4d03d07d86b1aa3`
  and linux/arm64 manifest `sha256:1ffb37fe66901e19bc1641824f0b8ae96eb83949e7888e4ef4a7fa47373c2201`,
  each with a linked attestation manifest. The locally pulled amd64 image ID
  was `sha256:38964ad919325828ba5998bbed7cec1c036119a229269511cae8b26617d9debf`.
  This run checked the index linkage and executed amd64; it did not inspect
  the attestation contents or execute arm64.
- Container limits: 512 MiB memory, 2 CPUs, 128 PIDs, `no-new-privileges`.
  Server limits: 4096-byte requests, two-second header/body deadlines, 32
  connections for the protocol suite. A second container used a two-connection
  cap and ten-second header deadline for overload probes. A synthetic bearer
  of at least 32 characters was supplied through a temporary mode-0600 env
  file and stdin, then deleted. The value was never committed or printed.
- No host port was published. Probes used the container's bridge address,
  `172.17.0.2:8085`, because this host previously had a Docker loopback port
  mapping timeout. This test does not qualify that mapping path.

Reproduce on an authorized Docker host after inspecting the image digest and
creating a synthetic token. Put only that token in a mode-0600 temporary env
file, use `LAB_ENV_FILE` for its path, then delete it after the run. Do not
commit or print the file. The commands below use `LAB_IP` from `docker inspect`
and read the same token on stdin. Run one container at a time:

```bash
docker pull ghcr.io/rhamenator/request-guard-mcp@sha256:0fd3f54fc331ab3ef9b0be45a7fc97a459038ebad1b37ebc68dec482b1eee597
docker buildx imagetools inspect ghcr.io/rhamenator/request-guard-mcp@sha256:0fd3f54fc331ab3ef9b0be45a7fc97a459038ebad1b37ebc68dec482b1eee597
umask 077
LAB_ENV_FILE=$(mktemp)
printf 'AUTH_TOKENS=%s\n' "$LAB_TOKEN" > "$LAB_ENV_FILE"
docker run -d --name request-guard-public-qual --env-file "$LAB_ENV_FILE" --memory 512m --cpus 2 --pids-limit 128 --security-opt no-new-privileges \
  -e MCP__HOST=0.0.0.0 -e MCP__PORT=8085 -e MCP__LIMITS__MAX_REQUEST_BYTES=4096 \
  -e MCP__LIMITS__HTTP_HEADER_TIMEOUT_SECS=2 -e MCP__LIMITS__HTTP_BODY_TIMEOUT_SECS=2 \
  -e MCP__LIMITS__MAX_CONNECTIONS=32 \
  ghcr.io/rhamenator/request-guard-mcp@sha256:0fd3f54fc331ab3ef9b0be45a7fc97a459038ebad1b37ebc68dec482b1eee597
LAB_IP=$(docker inspect request-guard-public-qual --format '{{range.NetworkSettings.Networks}}{{.IPAddress}}{{end}}')
printf '%s\n' "$LAB_TOKEN" | python3 scripts/adversarial_probe.py --url http://$LAB_IP:8085 --max-request-bytes 4096
printf '%s\n' "$LAB_TOKEN" | python3 scripts/adversarial_ws_probe.py --host "$LAB_IP" --port 8085 --max-request-bytes 4096
printf '%s\n' "$LAB_TOKEN" | python3 scripts/adversarial_classifier_probe.py --url http://$LAB_IP:8085
printf '%s\n' "$LAB_TOKEN" | python3 scripts/adversarial_transport_v014_probe.py --url http://$LAB_IP:8085
printf '%s\n' "$LAB_TOKEN" | python3 scripts/adversarial_envelope_fuzz_probe.py --url http://$LAB_IP:8085 --cases 128
printf '%s\n' "$LAB_TOKEN" | python3 scripts/adversarial_slow_client_probe.py --host "$LAB_IP" --port 8085 --max-request-bytes 4096
printf '%s\n' "$LAB_TOKEN" | python3 scripts/adversarial_backend_probe.py --url http://$LAB_IP:8085
docker stop request-guard-public-qual
docker rm request-guard-public-qual
```

Keep the inspected container address inside the owned lab network. For the two-slot overload run, start a fresh
container with the same limits and overrides, then supply its host PID:

```bash
docker run -d --name request-guard-public-cap --env-file "$LAB_ENV_FILE" --memory 512m --cpus 2 --pids-limit 128 --security-opt no-new-privileges \
  -e MCP__HOST=0.0.0.0 -e MCP__PORT=8085 -e MCP__LIMITS__MAX_REQUEST_BYTES=4096 \
  -e MCP__LIMITS__HTTP_BODY_TIMEOUT_SECS=2 -e MCP__LIMITS__MAX_CONNECTIONS=2 \
  -e MCP__LIMITS__HTTP_HEADER_TIMEOUT_SECS=10 \
  ghcr.io/rhamenator/request-guard-mcp@sha256:0fd3f54fc331ab3ef9b0be45a7fc97a459038ebad1b37ebc68dec482b1eee597
LAB_IP=$(docker inspect request-guard-public-cap --format '{{range.NetworkSettings.Networks}}{{.IPAddress}}{{end}}')

printf '%s\n' "$LAB_TOKEN" | python3 scripts/adversarial_connection_cap_probe.py --host "$LAB_IP" --port 8085
printf '%s\n' "$LAB_TOKEN" | python3 scripts/adversarial_connection_burst_probe.py --host "$LAB_IP" --port 8085 --attempts 128

docker stop request-guard-public-cap
docker rm request-guard-public-cap
python3 -c 'import os,sys; os.unlink(sys.argv[1])' "$LAB_ENV_FILE"
```

## Observed results

The authenticated suite passed 10/10 HTTP, 22/22 WebSocket, 19/19 classifier,
11/11 transport, 128/128 seeded malformed envelope, 4/4 slow-client/body
limit, and 2/2 Redis-unconfigured cases. The two-slot container passed 3/3
connection-cap cases and shed 128/128 burst attempts with zero probe errors
and a subsequent authenticated recovery.

The sustained probe ran for 63.15 seconds: 12 cycles each held two partial
headers and attempted 32 additional connections. All 384/384 excess
connections were shed, zero probe errors occurred, and authenticated ping
recovered after every cycle. Greatest sampled attempt latency was 1.37 ms,
below the two-second limit. Server RSS was 10,032 KiB before, 9,820 KiB after,
and 10,032 KiB at its sampled peak; sampled growth was zero, below the 16 MiB
probe bound. Host one-minute load samples ranged from 0.83 to 1.19, and I/O
PSI `some avg10` remained 0.00. These are observations from this host, not
general memory or performance guarantees.

Both containers remained healthy with zero restarts and no OOM event. Bounded
container logs (11,612 bytes for the protocol suite, 667 bytes for the
two-slot run) did not contain the synthetic bearer. The containers and token
files were removed, and the Docker service was returned to its prior inactive
state. No VM or host CA store was changed.

This supplements the [public native and client evidence](v0.1.5-public-qualification.md),
[Kali-to-Ubuntu adversarial run](v0.1.5-kali-ubuntu-adversarial.md), and
PostgreSQL, Redis, and TLS qualification. It is a bounded sample of the
published amd64 image. Stable v1.0 still needs a broader real-client matrix,
independent review of the complete gate, and owner approval under
[issue #125](https://github.com/rhamenator/request-guard-mcp/issues/125).

Native `ubuntu-24.04` amd64 and `ubuntu-24.04-arm` arm64 jobs each pulled by
digest, checked the selected Docker image architecture, and passed 51/51
bounded authenticated cases: 10 HTTP, 22 WebSocket, and 19 classifier. Both
jobs and the workflow concluded successfully; their logs had zero case
failures. Each container ran with 512 MiB memory, two CPUs, 128 PIDs,
`no-new-privileges`, a 4096-byte request limit, and an ephemeral synthetic
token read from a mode-0600 file. No host port was published. The containers
and token files were removed by the test script. The GitHub runners were
ephemeral; no local VM was used.

This later run adds actual published arm64 execution and a same-digest amd64
comparison. It does not repeat the earlier amd64 saturation, backend outage,
TLS, or synthetic-log probes on arm64. It also does not by itself satisfy the
final exact-candidate stable release gate or owner review in issue #125.
