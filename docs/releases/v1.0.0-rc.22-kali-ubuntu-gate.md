# Unpublished rc.22 cross-VM and musl PostgreSQL TLS gate

On 2026-10-23 UTC, Kali `copperfin-kali-full` probed the exact unpublished
v1.0.0-rc.22 Linux x64 glibc archive running on Ubuntu
`copperfin-ubuntu26-deb`. A separate disposable Alpine container probed the
matching musl archive's PostgreSQL TLS trust behavior. This is bounded
candidate evidence, not approval to publish stable v1.0.

The PostgreSQL and Redis stage results above were observed in the operator
terminal; their raw guest stdout was not retained in Git. PostgreSQL
classification during outage is an expected upstream-error path for this
configured persistent-decision backend, not a claim of general availability.

PostgreSQL used disposable database `request_guard_rc22_lab` under peer
authentication. The existing PostgreSQL cluster was stopped and restarted
for the outage probe, verified online afterward, and the test database was
removed. Disposable Redis was stopped and removed. The three nonempty MCP
logs were 10,468, 2,139 and 1,835 bytes, each under 64 KiB. Operator-run
exact-string checks found no synthetic bearer, HMAC or seeded indicator in
those scoped MCP logs. The raw guest logs were removed with the temporary
files; they are not retained as independent evidence. Encoded/truncated forms
and backend logs were not searched. The operator removed guest processes,
copied files and the test database, then verified Kali and Ubuntu off with
libvirt; the preexisting Copperfin Windows guest was untouched.
Host I/O PSI `full avg10` was 0.00 before VM boot and 2.81 after Docker TLS
testing and VM shutdown. These point samples do not characterize the whole
run.

## PostgreSQL TLS trust and limits

`scripts/smoke_alpine_postgres_tls.py` ran the exact extracted rc.22 musl
binary in pinned Alpine 3.24.2 base image
`sha256:294b683cb724975bec92580e1e685676bd4b50bda910ddb8c51d4cabeaec77e6`.
It passed explicit trusted CA, untrusted CA rejection, hostname mismatch,
unmodified OS-store rejection and OS-store trust after installing a test CA
**inside the disposable container**. It checked bounded private MCP logs and
`serverInfo.version`; these assertions are in
`scripts/alpine_postgres_tls.py`, while the console prints one aggregate PASS.
PostgreSQL and MCP both used container loopback;
PostgreSQL used trust authentication. Docker's default network permitted live
`apk` installation; exact package revisions were not recorded. The container
was removed and Docker had no running containers afterward. No host/guest CA
store was changed.

Cross-VM checks exercised glibc; PostgreSQL TLS trust exercised musl. This
does not prove glibc or other-platform TLS parity, production TLS termination,
remote database failover, Redis TLS, distributed ingress fairness, scanner
capture counts, all-client compatibility or a 256-client deployment. No
public v1 tag, release, GHCR image, npm package or Agensi ZIP was created.
Complete adversarial LLM review, owner approval and approved-tag public
artifact verification remain in
[issue #125](https://github.com/rhamenator/request-guard-mcp/issues/125).
