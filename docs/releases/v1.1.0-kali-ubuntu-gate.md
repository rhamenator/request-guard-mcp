# v1.1.0 cross-VM adversarial replay (Kali attacker, Ubuntu server)

This is bounded evidence for the **published** `v1.1.0` Linux x64 glibc archive, run on 2026-11-20
after publication. It repeats the lab step that the
[v1.1.0-rc.1](v1.1.0-rc.1-release-record.md) and [v1.1.0](v1.1.0-release-record.md) release
records list as "not done". **No independent human review took place**: the operator was an AI
model (Claude) driving the lab through the repository's own probe scripts.

## Artifact identity and setup

- Archive `request-guard-mcp-v1.1.0-linux-x64.tar.gz`, SHA-256
  `4b8a78e3269da36748424cefaf085fbb556c95d835049e15c1807b7e9fabcc75`, downloaded from the
  GitHub release and checked against its sidecar. The Ubuntu guest independently returned the same
  digest before extraction; the extracted binary's SHA-256 was
  `38f28a528652300a76355ab57e1db1fe858a6e6162a33a6658f8fb31e41e1199`.
- Server: Ubuntu 26.04 guest `192.168.122.73`, bound to that lab address only. Attacker: Kali Linux
  2026.2 guest `192.168.122.74`. Both are libvirt NAT guests on one owned host; nothing was exposed
  beyond it.
- Configuration followed the CI harness: `MAX_REQUEST_BYTES` 4096, one-second header and body
  deadlines, auth enabled. The bearer token (and, for PostgreSQL, the cache-scope key) was random,
  synthetic, passed over SSH to the lab guests and never written to the host's disk. Every probe's
  output was checked for the literal token before it was saved. The five server logs (11 to 2.6 kB)
  contained no match for the token or the key.
- The binary has no `--version` flag (it prints usage); version identity rests on the archive and
  binary digests above.

## Results

Every group passed. The sanitized records are in
[v1.1.0-kali-ubuntu-probes.jsonl](v1.1.0-kali-ubuntu-probes.jsonl) (134 records).

| Probe | Passed / total |
| --- | ---: |
| HTTP MCP and authentication | 10 / 10 |
| WebSocket MCP | 22 / 22 |
| Classifier evasion | 19 / 19 |
| Pinned transport (MCP 2025-06-18) | 11 / 11 |
| Pinned JSON-RPC envelopes | 13 / 13 |
| Bounded malformed envelopes and recovery | 128 / 128 |
| Slow and partial clients, body limit | 4 / 4 |
| No optional backend: error and core recovery | 2 / 2 |
| Connection cap (two slots) | 3 / 3, plus a 128-attempt shedding burst |
| **New:** `robots_violation` input | 18 / 18 (58 requests) |
| Redis: healthy, outage, restarted | 2 / 2 each stage |
| PostgreSQL: healthy, cluster stopped, restarted | 3 / 3 each stage |

The new probe, `scripts/adversarial_robots_violation_probe.py`, checks that the field blocks when
`true`; that `false` equals absent; that strings, integers, `null`, arrays, objects, a 10^30 integer
and an empty string are rejected rather than coerced; that the signal cannot be smuggled through
`extra` or a header; that a misspelled neighbour field is rejected; that a duplicate key does not
crash the server; that `explain`, `score_breakdown` and `batch_classify` accept the field; that 40
alternating requests leave no residue; and that the server is healthy afterwards.

Redis and PostgreSQL were disposable (a loopback Redis on port 16379 with one seeded record, and a
database created and dropped for the run). The Redis process and the PostgreSQL cluster were
stopped and restarted on the guest; `classify` kept working during both outages and the dependent
tools returned `-502`/`UPSTREAM_ERROR` and then recovered. The guest's PostgreSQL cluster was
accepting connections again at the end.

## Scanners (Kali, owned lab endpoint only)

- `nmap -sV -p 18095`: one open TCP port, reported as `tcpwrapped`, no service banner.
- `nmap -p 1-1000 --max-rate 100`: only SSH (22) open on the guest; 999 ports closed.
- `nikto -maxtime 60s` against the MCP port: 7,179 requests in 5 seconds, 0 errors, 5 informational
  items, all missing browser security headers (referrer-policy, permissions-policy,
  content-security-policy, strict-transport-security, a deprecated X-Frame-Options note). The
  server speaks JSON over HTTP behind a trusted proxy, so those headers belong to the ingress; they
  are not findings against the MCP protocol.
- The server stayed up; its log had no panic and no token match after the scans.

## Limits

- One run on one host, Linux x64 glibc only. The musl, Windows and macOS archives and the
  container were not part of this lab replay.
- Sustained connection exhaustion, TLS on the wire, and the PostgreSQL TLS probe were not repeated.
- Request Guard was exercised over loopback-class lab addressing without a TLS terminator.
- The cross-VM binding to the release rests on the digest observations above, not on signed remote
  attestation. The attestation signatures of the release archives were still not verified
  cryptographically.
- Scanner results are bounded and unauthenticated; they are not a penetration test.
- Guest cleanup (removing `/tmp/rg-lab`, killing the listeners) succeeded; both VMs were shut off
  afterwards. The host's synthetic token existed only in process memory.
