# Public v0.1.5 PostgreSQL outage and recovery

On 2026-10-21 (America/Detroit), Kali `copperfin-kali-full` exercised
PostgreSQL-backed tools on Ubuntu `copperfin-ubuntu26-deb`. Ubuntu ran the
**published** v0.1.5 Linux x64 glibc archive, not a locally rebuilt server.
This is one bounded outage cycle for the v1.0 release gate, not a general
availability or TLS qualification.

## Exact artifact and scope

- Tag commit: `f76ff9d2558fac705f091d9b858d3bc180b4f0bd`.
- [Public archive](https://github.com/rhamenator/request-guard-mcp/releases/download/v0.1.5/request-guard-mcp-v0.1.5-linux-x64.tar.gz)
  `request-guard-mcp-v0.1.5-linux-x64.tar.gz` SHA256:
  `7e1b9f25719de1a2e0db8803167188de7df161d1df3c15b22bd67385320aacc0`.
  Its public sidecar passed `sha256sum -c` **inside Ubuntu**.
- Extracted binary SHA256:
  `2c68a15272619d9b2240303815f4dcf61bc283eac3d022deb3227ea17711e25f`.
- Kali used `scripts/adversarial_postgres_probe.py` SHA256
  `10d7fc5ed2e499cc39ec4cb16671bfd001ef5e1854147017d8727e010d901cec`
  and its `scripts/adversarial_probe.py` dependency SHA256
  `7a9a91be25a810778e510b3e573ec39cfacdc42efc70840dd11f1be6a1fb674c`
  from main `10185c6`.
- Ubuntu endpoint was `192.168.122.73:18091` on the isolated libvirt network;
  Kali was `192.168.122.74`. PostgreSQL 18 was installed in Ubuntu and
  accessed through its local Unix socket. This did **not** test database TLS,
  a remote database, replicas, concurrency, or an untrusted network.
- The server used fresh synthetic 64-character bearer and cache-scope HMAC
  values, a 4,096-byte request cap, two-second header/body deadlines, and a
  32-connection cap. The bearer was passed to Kali over SSH and read by the
  probe on stdin. Neither value was committed or printed in the evidence.

## Procedure and observations

The Ubuntu guest verified the public archive with its `.sha256` sidecar and
`sha256sum -c`, extracted it with `tar -xzf`, and checked the binary hash
above. PostgreSQL 18 was already installed in that guest; the lab created a
disposable `copperfin` PostgreSQL role and `request_guard_lab` database. The
server ran as OS user `copperfin`, which authenticated to the local socket
through PostgreSQL peer authentication. It used
`MCP__POSTGRES__URL=postgresql:///request_guard_lab?host=/var/run/postgresql`
and `MCP__AUTH__CACHE_SCOPE_HMAC_KEY`, and remained running throughout.

For a disposable Ubuntu lab, prepare PostgreSQL and launch the verified
extracted binary with values generated locally in that guest:

```bash
sudo -u postgres createuser --login copperfin
sudo -u postgres createdb --owner=copperfin request_guard_lab
umask 077
PRIVATE_TOKEN_FILE=/tmp/request-guard-pg-token
PRIVATE_HMAC_FILE=/tmp/request-guard-pg-hmac
openssl rand -hex 32 > "$PRIVATE_TOKEN_FILE"
openssl rand -hex 32 > "$PRIVATE_HMAC_FILE"
AUTH_TOKENS="$(cat "$PRIVATE_TOKEN_FILE")" \
MCP__AUTH__CACHE_SCOPE_HMAC_KEY="$(cat "$PRIVATE_HMAC_FILE")" \
MCP__HOST=192.168.122.73 MCP__PORT=18091 \
MCP__POSTGRES__URL='postgresql:///request_guard_lab?host=/var/run/postgresql' \
MCP__LIMITS__MAX_REQUEST_BYTES=4096 \
MCP__LIMITS__HTTP_HEADER_TIMEOUT_SECS=2 \
MCP__LIMITS__HTTP_BODY_TIMEOUT_SECS=2 \
MCP__LIMITS__MAX_CONNECTIONS=32 \
./request-guard-mcp-v0.1.5-linux-x64/request-guard-mcp
```

Transfer the synthetic bearer to an owner-readable file on Kali over the
authorized SSH connection before running the probes. In this run, an SSH
pipeline copied only the file contents directly between guest sessions;
neither value appeared in a process argument. Do not transfer the cache-scope
HMAC value. Run the Kali commands from a checkout containing the two pinned
probe scripts; they use that local bearer file. Kali ran the same synthetic
request ID at each stage:

```bash
PRIVATE_TOKEN_FILE=/tmp/request-guard-pg-token
cat "$PRIVATE_TOKEN_FILE" | python3 scripts/adversarial_postgres_probe.py \
  --url http://192.168.122.73:18091 --stage healthy \
  --request-id public-v015-pg-lab-001
# On Ubuntu: sudo pg_ctlcluster 18 main stop
cat "$PRIVATE_TOKEN_FILE" | python3 scripts/adversarial_postgres_probe.py \
  --url http://192.168.122.73:18091 --stage outage \
  --request-id public-v015-pg-lab-001
# On Ubuntu: sudo pg_ctlcluster 18 main start
cat "$PRIVATE_TOKEN_FILE" | python3 scripts/adversarial_postgres_probe.py \
  --url http://192.168.122.73:18091 --stage healthy \
  --request-id public-v015-pg-lab-001
```

The example token file should be owner-readable (`chmod 600`) and contain a
fresh synthetic value of at least 32 characters. The server receives its
bearer and HMAC in process environment variables, which privileged local
processes can inspect. Binding plain HTTP on this address is appropriate
only for the isolated lab network.

| Stage | `classify` | `replay_decision` | MCP `ping` | Probe verdict |
| --- | --- | --- | --- | --- |
| PostgreSQL healthy | HTTP 200, successful result | HTTP 200, `matches_original=true` | HTTP 200 | 3/3 |
| PostgreSQL stopped | HTTP 200, JSON-RPC `-502 UPSTREAM_ERROR` | HTTP 200, JSON-RPC `-502 UPSTREAM_ERROR` | HTTP 200 | 3/3 |
| PostgreSQL restarted | HTTP 200, successful result | HTTP 200, `matches_original=true` | HTTP 200 | 3/3 |

The bounded, nonempty 2,063-byte server log was measured with `wc -c` on
Ubuntu. This matches the size observed in the older candidate run by
coincidence; the value was read from the new v0.1.5 run before cleanup.
`grep -F -q -f` with each guest-local secret file found neither the synthetic
bearer nor the synthetic HMAC value in that log. That
is a scoped log check, not proof against all possible secret leakage. The
database, role, server process, copied archive/binary, probe copies, and
temporary tokens/logs were removed. PostgreSQL was stopped after the run;
both lab VMs shut down cleanly. The existing `copperfin-vfp9-win11` guest
was left untouched. No firewall change was needed. Host I/O PSI `some avg10`
was 0.00 before boot and after probes; load rose from 0.83 to 2.82.

This confirms one healthy/outage/recovery sequence and a successful MCP
`ping` while PostgreSQL was down. Redis health/recovery, PostgreSQL TLS trust,
multi-client load, database failover, and the full packaged image/adversarial
gate remain open in [issue #125](https://github.com/rhamenator/request-guard-mcp/issues/125).
