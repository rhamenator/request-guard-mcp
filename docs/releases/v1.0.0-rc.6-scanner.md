# Private v1.0.0-rc.6 Kali-to-Ubuntu scanner capture

On 2026-10-22, Kali `copperfin-kali-full` scanned only the owned Ubuntu
`copperfin-ubuntu26-deb` endpoint `192.168.122.73:18086`. Ubuntu ran the
**private**, unmerged Linux x64 archive produced by workflow
[`39756083268`](https://github.com/rhamenator/request-guard-mcp/actions/runs/39756083268)
from draft PR #149 commit `aa631dae14346822b1a9dc94fb77395be4376015`.
This qualifies one scanner slice of **that unmerged commit only**, not this
documentation branch, public v1.0 release evidence or a complete stable
release gate. The workflow run and draft PR state were checked on GitHub.

## Artifact and lab

- Archive `request-guard-mcp-v1.0.0-rc.6-linux-x64.tar.gz` SHA256:
  `eecdc6eaf90b4209e4615467a7a99933b67ca8ecb4ee7cb9ceeaba71f26374a3`.
  Its workflow sidecar passed `sha256sum -c` on the host and again inside
  Ubuntu. Extracted binary SHA256:
  `91d7355d0602974552668d15be85dbe307888e88dca21e4a2d617e1bc6b1f707`.
  Startup log identified version `1.0.0` and listener `0.0.0.0:18086`.
- The private libvirt `default` NAT network (`virbr0`, `192.168.122.0/24`)
  used plain HTTP and a new 64-character
  synthetic bearer in a mode-0600 guest file. The server had a 4,096-byte
  request cap, two-second header/body deadlines and 32 connection slots.
  No backend, TLS proxy or external collector was configured for this test.
  NAT permits outbound access; this was not a network with forwarding disabled.
- Kali (`192.168.122.74`) used Nmap 7.99 and Nikto 2.6.1 without the bearer.
  Ubuntu captured
  each run separately with `tcpdump -U -i any -s 0` and filter
  `host 192.168.122.74 and tcp port 18086`. TShark and the committed
  `scripts/verify_scanner_capture.py` counted message boundaries in every
  stream and checked for retransmissions. The operator separately read
  tcpdump's stop summaries: each final capture had equal captured/received
  packet totals and **zero kernel drops**. That observation does not prove
  the capture contains every packet sent outside the capture window.
  Host TShark was 4.6.4. The verifier hardcodes Kali's source IP.

Both capture-verifier runs passed with zero retransmissions. Nikto's six
messages that TShark did not decode as HTTP requests used malformed request
lines; the verifier counted one response segment per client message, without
mapping response status to each request. Nmap sent a
`JDWP-Handshake` service probe, received HTTP 400, called the port
`tcpwrapped`, then stopped. An earlier run of the same command independently
had the same one-message outcome against the same server process (20/20
captured/received, zero drops).
This differs from the 30 Nmap messages in the public v0.1.5 scan, so **30
must not be reused as this candidate's request count**. Nmap's HTTP scripts
and broader version probes were therefore not exercised. The cause of the
different early-stop behavior is **unresolved**; an A/B run against the
public v0.1.5 binary under identical lab settings would be needed before
attributing it to the scanner or server. Nikto reached the HTTP endpoint and
reported suggestions for `permissions-policy`, `strict-transport-security`,
`referrer-policy` and `content-security-policy`. These plain-HTTP lab
observations say nothing about production TLS/proxy headers. No MCP defect
was established by these captures. After both scans, an authenticated
JSON-RPC `ping` returned HTTP 200 with a valid result; `pgrep` still showed
the original server PID 3314 before cleanup.

TShark decoded no `http.authorization` field in either capture using
`tshark -r FILE -Y 'http.authorization' -T fields -e http.authorization`.
The token was not provided to either scanner, so this check says little about
secret handling. These unauthenticated scans mainly exercised the pre-auth
gate and error paths, not authenticated MCP tools. Nikto was limited to
`-Tuning 1234` and a 15-second execution window; it was not a full scan.
Raw pcaps are retained locally
under `dist/v1.0.0-rc.6-scanner/`, outside Git and release assets.

## Reproduce and limits

Verify the private archive sidecar and extract it in Ubuntu. Generate a
fresh synthetic bearer. The tested `0.0.0.0` bind listens on every guest
interface; use it only when guest networking/firewall rules confine access
to the authorized lab. Otherwise bind `MCP__HOST` to the intended lab
interface address. The following reproduces the tested configuration:

```bash
AUTH_TOKENS="$(cat PRIVATE_TOKEN_FILE)" MCP__HOST=0.0.0.0 MCP__PORT=18086 \
  MCP__LIMITS__MAX_REQUEST_BYTES=4096 \
  MCP__LIMITS__HTTP_HEADER_TIMEOUT_SECS=2 \
  MCP__LIMITS__HTTP_BODY_TIMEOUT_SECS=2 \
  MCP__LIMITS__MAX_CONNECTIONS=32 \
  ./request-guard-mcp-v1.0.0-rc.6-linux-x64/request-guard-mcp
```

Capture Nmap and Nikto separately with immediate writes. Stop each capture
after its scanner exits; check tcpdump's captured, received and dropped
counts, then run `python3 scripts/verify_scanner_capture.py --pcap FILE
--scanner nmap` (or `nikto`). A passing verifier establishes observed wire
message boundaries for that capture, not a fixed future scanner count.

Host load was 0.50 before guest boots, briefly 2.45 during staggered boots,
and 0.45 after tests; sampled I/O PSI `full avg10` was 0.00, 1.60 and 0.00
at those points. The lab server, temporary bearer and both VMs were stopped;
both guests were verified off. This was a single private glibc build on a
private NAT lab network, not the final published image, other architectures,
production TLS or complete Kali-to-Ubuntu adversarial replay.
