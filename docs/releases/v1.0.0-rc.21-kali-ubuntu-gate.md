# Private rc.21 cross-VM and PostgreSQL TLS gate

On 2026-10-23 UTC, Kali `copperfin-kali-full` exercised the exact **private,
unpublished** v1.0.0-rc.21 Linux x64 glibc archive on Ubuntu
`copperfin-ubuntu26-deb`. A separate disposable Alpine container exercised
the matching private musl archive's PostgreSQL TLS trust behavior. This is a
bounded candidate replay, not approval to publish stable v1.0.

An initial slow-client pass failed its two deadline assertions because the
lab launcher used nonexistent `MCP__LIMITS__HEADER_READ_TIMEOUT_SECS` and
`MCP__LIMITS__BODY_READ_TIMEOUT_SECS` settings, leaving the defaults in place.
After restarting the same verified binary with the actual
`MCP__LIMITS__HTTP_HEADER_TIMEOUT_SECS` and
`MCP__LIMITS__HTTP_BODY_TIMEOUT_SECS` settings, all four
checks passed. This was a test setup error; the failed pass is retained here.

The PostgreSQL test created disposable database `request_guard_rc21_lab`
under peer authentication, stopped/restarted the existing PostgreSQL 18
cluster and verified it online afterward, then removed the test database.
Disposable Redis ran without persistence on port 16379 and was stopped.
The MCP processes and temporary copied files, scripts and synthetic secrets
were removed. Exact-string checks found no synthetic bearer, HMAC or seeded
indicator in the scoped core/PostgreSQL/Redis **MCP logs**, which were
respectively 1,277, 2,139 and 1,835 bytes (each under 64 KiB).
Encoded/truncated forms and backend logs were not searched. Kali shut down
normally. Ubuntu stopped accepting SSH after an in-guest graceful shutdown
request but libvirt still reported it running, so the already unreachable
guest was powered off through libvirt. Both guests were verified off; the
preexisting Copperfin Windows guest was untouched.
Host I/O PSI `full avg10` was 0.00 before boot and 0.16 after shutdown
was initiated. These point samples do not characterize the whole run.
Libvirt `virsh list --state-running` confirmed only the preexisting Windows
guest running after cleanup. No firewall or host trust-store change was made.

## PostgreSQL TLS trust and limits

`scripts/smoke_alpine_postgres_tls.py` ran the exact extracted private musl
binary in pinned Alpine 3.24.2 base image
`sha256:294b683cb724975bec92580e1e685676bd4b50bda910ddb8c51d4cabeaec77e6`.
It passed explicit trusted CA, untrusted CA rejection, hostname mismatch,
unmodified OS-store rejection and OS-store trust after installing a test CA
**inside the disposable container**. It required specific rustls rejection
causes for untrusted CA and hostname mismatch, checked `serverInfo.version`,
and required nonempty bounded MCP logs for each case. Exact synthetic
bearer/HMAC strings were absent from the checked logs. PostgreSQL and MCP
both used container loopback; PostgreSQL used trust authentication. Docker's
default network permitted live `apk`
installation; exact package versions were not recorded. No host/guest CA
store was changed. The test container was removed and Docker returned to its
initially inactive service state.

The cross-VM checks exercised glibc; PostgreSQL TLS trust was exercised on
musl. This does not prove glibc or other-platform TLS parity, production TLS
termination, remote database failover, Redis TLS, distributed ingress
fairness, scanner capture counts, all-client compatibility or a 256-client
deployment. No public v1 tag, release, GHCR image, npm package or Agensi ZIP
was created. Complete adversarial LLM review, owner approval and approved-tag
public artifact verification remain in
[issue #125](https://github.com/rhamenator/request-guard-mcp/issues/125).
