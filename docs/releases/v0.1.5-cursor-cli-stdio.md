# Cursor CLI stdio client check against public v0.1.5

On 2026-10-21, Cursor Agent CLI version `2026.10.19-6bbf2c4`, signed into
the maintainer's Cursor account, connected to the checksum-verified **public** Linux
x64 glibc v0.1.5 executable over process-local stdio. The release archive
SHA256 was `7e1b9f25719de1a2e0db8803167188de7df161d1df3c15b22bd67385320aacc0`;
the extracted executable SHA256 was
`2c68a15272619d9b2240303815f4dcf61bc283eac3d022deb3227ea17711e25f`.
The archive was downloaded from the [v0.1.5 GitHub release](https://github.com/rhamenator/request-guard-mcp/releases/tag/v0.1.5)
and checked against its `.sha256` sidecar before extraction. No server bearer
token, optional backend, VM, or Docker service was used. Cursor account login
does not authenticate the process-local MCP server.

A temporary test workspace held only this `.cursor/mcp.json` entry; it was not
a security sandbox:

```json
{"mcpServers":{"request-guard-test":{"command":"/path/to/verified/request-guard-mcp","args":["--stdio"]}}}
```

`agent mcp list` found the entry, and `agent mcp list-tools request-guard-test`
advertised 23 tools, including `classify` and `explain`; only `classify` was
invoked. The following command records the maintainer's synthetic test, **not
a recommended buyer setup**. `--trust` bypassed the workspace trust prompt,
while `--force` permitted tool calls without interactive approval. Use normal
interactive approval for routine use; no safer noninteractive approval path
was verified in this test.

```bash
agent --trust --force --approve-mcps --workspace "$LAB_WORKSPACE" \
  --mode ask -p --output-format stream-json \
  'Use the request-guard-test MCP server only. Call its classify tool exactly once with synthetic metadata: ip 198.51.100.42, method GET, path /docs, user_agent Cursor-Qualification/1. Report the verdict and tool name. Do not run shell commands or edit files.'
```

The maintainer's local trace showed one `getMcpToolsToolCall` for the `classify` schema and one
`mcpToolCall` to `request-guard-test-classify` with exactly those four
synthetic arguments. The MCP result had `isError:false`, structured content
with `verdict:"flag"`, `score:0.7`, and one `ua_non_browser` signal. Cursor's
final answer reported `flag`. This is an observed response to a synthetic
user-agent, not a validation of classification accuracy. The process exited
zero. The raw trace remains
local, outside Git, because it includes Cursor session identifiers; its
SHA256 was `e273561db06a0450151a68fee158166b87c0c99230dd991f6f1b926c7fd6eba9`.
The trace details are maintainer-attested rather than independently inspectable
from this document.

In the same noninteractive mode, `--trust` alone did not suffice: the MCP call
was rejected as `User rejected MCP` even after `agent mcp enable` and
`--approve-mcps`. Adding `--force` let this test proceed. The trace did not expose the initialization handshake or
negotiated MCP protocol version. This is one successful Cursor CLI stdio tool
call, not proof of its graphical UI, HTTP, cancellation behavior, all tools,
prompt-injection resistance, repeat-run stability, or other host platforms and
Cursor versions. It supplies one real-client data point toward the open stable
gate; it does not complete that gate. Stdio trusts the launching local process and does
not use HTTP bearer or Origin controls; PostgreSQL is unavailable in this
mode. See the [stable-release gate](https://github.com/rhamenator/request-guard-mcp/issues/125).
