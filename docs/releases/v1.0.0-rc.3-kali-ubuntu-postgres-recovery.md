# Private v1.0.0-rc.3 PostgreSQL outage and recovery

On 2026-10-22 (UTC), Kali `copperfin-kali-full` exercised the **private,
unpublished** v1.0.0-rc.3 Linux x64 archive on Ubuntu
`copperfin-ubuntu26-deb`. This is one bounded PostgreSQL outage cycle against
the exact candidate from draft PR #149, not a stable release qualification by
itself. No `v1.0.0` tag or public release was created.

## Artifact and setup

- Candidate commit: `bc03b2ac878ccecdc3b2a648c98181587d314e37`.
- Private five-platform release workflow: [39715909418](https://github.com/rhamenator/request-guard-mcp/actions/runs/39715909418).
- The downloaded `request-guard-mcp-v1.0.0-rc.3-linux-x64.tar.gz` passed its
  bundled `sha256sum -c` **inside Ubuntu**. Its extracted binary SHA256 was
  `bd7e7ec539873aa36c5d1fb378af0eec5c2341cb8c77d24f273b2e86ab9a7436`.
- Kali ran `scripts/adversarial_postgres_probe.py` SHA256
  `10d7fc5ed2e499cc39ec4cb16671bfd001ef5e1854147017d8727e010d901cec`
  and `scripts/adversarial_probe.py` SHA256
  `7a9a91be25a810778e510b3e573ec39cfacdc42efc70840dd11f1be6a1fb674c`.
- The Ubuntu server bound plain HTTP to the isolated libvirt address
  `192.168.122.73:18091`; Kali used `192.168.122.74`. PostgreSQL 18 used a
  guest-local Unix socket, peer authentication, a disposable role and database.
  The server had a fresh synthetic 64-character bearer and cache-scope HMAC,
  a 4,096-byte request cap, two-second header/body deadlines, and a
  32-connection cap. The bearer was piped between guest SSH sessions into an
  owner-readable Kali file; the HMAC stayed in Ubuntu. Neither value is in
  this repository.

The Ubuntu guest extracted the checksum-verified archive under `/tmp` and
started its binary as the `copperfin` user with these nonsecret settings:

```bash
MCP__HOST=192.168.122.73 MCP__PORT=18091 \
MCP__POSTGRES__URL='postgresql:///request_guard_lab?host=/var/run/postgresql' \
MCP__LIMITS__MAX_REQUEST_BYTES=4096 \
MCP__LIMITS__HTTP_HEADER_TIMEOUT_SECS=2 \
MCP__LIMITS__HTTP_BODY_TIMEOUT_SECS=2 \
MCP__LIMITS__MAX_CONNECTIONS=32 \
AUTH_TOKENS="$(cat /tmp/rg-rc3-token)" \
MCP__AUTH__CACHE_SCOPE_HMAC_KEY="$(cat /tmp/rg-rc3-hmac)" \
./request-guard-mcp-v1.0.0-rc.3-linux-x64/request-guard-mcp
```

Both secret files were generated inside Ubuntu with `umask 077` and
`openssl rand -hex 32`. The synthetic bearer was copied to Kali through an
SSH pipe, without putting it in a command argument. Kali ran the same
request ID at all three stages:

```bash
cat /tmp/rg-rc3-token | python3 adversarial_postgres_probe.py \
  --url http://192.168.122.73:18091 --stage healthy \
  --request-id private-v100-rc3-pg-lab-001
# On Ubuntu: sudo pg_ctlcluster 18 main stop
cat /tmp/rg-rc3-token | python3 adversarial_postgres_probe.py \
  --url http://192.168.122.73:18091 --stage outage \
  --request-id private-v100-rc3-pg-lab-001
# On Ubuntu: sudo pg_ctlcluster 18 main start
cat /tmp/rg-rc3-token | python3 adversarial_postgres_probe.py \
  --url http://192.168.122.73:18091 --stage healthy \
  --request-id private-v100-rc3-pg-lab-001
```

## Observations and limits

| Stage | `classify` | `replay_decision` | MCP `ping` | Probe verdict |
| --- | --- | --- | --- | --- |
| Healthy | HTTP 200, successful result | HTTP 200, `matches_original=true` | HTTP 200 | 3/3 |
| PostgreSQL stopped | HTTP 200, JSON-RPC `-502 UPSTREAM_ERROR` | HTTP 200, JSON-RPC `-502 UPSTREAM_ERROR` | HTTP 200 | 3/3 |
| PostgreSQL restarted | HTTP 200, successful result | HTTP 200, `matches_original=true` | HTTP 200 | 3/3 |

The bounded server log was nonempty (2,063 bytes). Guest-local exact-string
searches found neither synthetic bearer nor HMAC in it. This is a scoped log
check, not a general proof against secret leakage.

An initial simultaneous two-VM boot was aborted **before any probe** when host
I/O PSI `full avg10` reached 19.70 and load reached 8.04. Both guests were
shut down. A later staggered boot started with host I/O PSI at 0.00; after
the three probe stages, `full avg10` was 0.01 and load was 2.67. The
disposable database/role, guest archive, server process, token files, probe
copies and logs were removed. PostgreSQL was restored to its initially online
state, and both lab guests were shut down. No firewall rule changed.

This test does not exercise PostgreSQL TLS, a remote database, failover,
concurrent clients, Redis, or the full v1.0 candidate matrix. Those and owner
review remain in [issue #125](https://github.com/rhamenator/request-guard-mcp/issues/125).
