# Private v1.0.0-rc.3 Redis outage and recovery

On 2026-10-22 (UTC), Kali `copperfin-kali-full` exercised a seeded Redis
lookup on Ubuntu `copperfin-ubuntu26-deb` using the **private, unpublished**
v1.0.0-rc.3 Linux x64 glibc archive from draft PR #149. This is one bounded
backend cycle, not full v1.0 qualification. No stable tag or public release
was created.

## Candidate and lab setup

- Candidate commit: `bc03b2ac878ccecdc3b2a648c98181587d314e37`.
  [Private workflow 39715909418](https://github.com/rhamenator/request-guard-mcp/actions/runs/39715909418)
  succeeded with this `headSha`; `gh run download 39715909418` retrieved
  artifact `request-guard-mcp-linux-x64`.
- Archive SHA256 on the downloaded host copy:
  `cc92344b955fc86602763acf09f5a10651ca7256f78cd45fcad1bf24fc522313`.
  Its bundled `.sha256` sidecar passed `sha256sum -c` inside Ubuntu after
  transfer. The extracted binary SHA256 inside Ubuntu was
  `bd7e7ec539873aa36c5d1fb378af0eec5c2341cb8c77d24f273b2e86ab9a7436`.
  The sidecar and archive share build provenance; no independent attestation
  or workflow-recorded archive digest was compared.
- Kali ran `scripts/adversarial_redis_recovery_probe.py` SHA256
  `2933e9b532989f1a958c3be9d1d231ad3a202d19d8aba20f4042dc3a37b33c0d`
  and `scripts/adversarial_probe.py` SHA256
  `7a9a91be25a810778e510b3e573ec39cfacdc42efc70840dd11f1be6a1fb674c`
  from the candidate commit. Both were compared with
  `git show bc03b2a:scripts/adversarial_redis_recovery_probe.py | sha256sum`
  and the analogous `adversarial_probe.py` command. They require only
  Python's standard library.
- Kali `192.168.122.74` contacted the Ubuntu MCP endpoint
  `192.168.122.73:18092` on the isolated libvirt network. Redis 8.0.5 ran
  only on Ubuntu loopback `127.0.0.1:16379`, without persistence. The default
  Redis service was inactive before testing. No firewall command was run.
- The MCP server used a fresh synthetic 64-character bearer, a 4,096-byte
  request cap, two-second header/body deadlines, a 32-connection cap, and
  `MCP__REDIS__KEY_PREFIX=ci_probe`. Ubuntu created the bearer with `umask 077`
  and `openssl rand -hex 32`; an SSH pipe copied it to an owner-readable Kali
  file without exposing the value in a command argument. No real credentials
  or indicators were used.

Ubuntu verified and extracted the archive under `/tmp`, then started a
disposable Redis process and seeded one test record:

```bash
sha256sum -c request-guard-mcp-v1.0.0-rc.3-linux-x64.tar.gz.sha256
tar -xzf request-guard-mcp-v1.0.0-rc.3-linux-x64.tar.gz
sha256sum request-guard-mcp-v1.0.0-rc.3-linux-x64/request-guard-mcp
redis-server --bind 127.0.0.1 --port 16379 --save '' --appendonly no \
  --loglevel warning > /tmp/rg-rc3-redis.log 2>&1 &
echo $! > /tmp/rg-rc3-redis.pid
redis-cli -h 127.0.0.1 -p 16379 HSET ci_probe:threats:domain \
  ci-v100-rc3-redis.example \
  '{"threat_type":"ci_probe","severity":"high","source":"request_guard_lab"}'
```

The `.example` suffix makes this indicator a domain lookup. Ubuntu launched
the extracted MCP binary with the following settings; `openssl rand -hex 32`
had created the single-line bearer file under `umask 077`. Both process IDs
were recorded for cleanup.

```bash
AUTH_TOKENS="$(cat /tmp/rg-rc3-redis-token)" \
MCP__HOST=192.168.122.73 MCP__PORT=18092 \
MCP__REDIS__URL=redis://127.0.0.1:16379 \
MCP__REDIS__KEY_PREFIX=ci_probe \
MCP__LIMITS__MAX_REQUEST_BYTES=4096 \
MCP__LIMITS__HTTP_HEADER_TIMEOUT_SECS=2 \
MCP__LIMITS__HTTP_BODY_TIMEOUT_SECS=2 \
MCP__LIMITS__MAX_CONNECTIONS=32 \
./request-guard-mcp-v1.0.0-rc.3-linux-x64/request-guard-mcp \
  > /tmp/rg-rc3-redis-mcp.log 2>&1 &
echo $! > /tmp/rg-rc3-redis-mcp.pid
```

Kali ran the same probe at each stage:

```bash
cat /tmp/rg-rc3-redis-token | python3 adversarial_redis_recovery_probe.py \
  --url http://192.168.122.73:18092 --stage healthy \
  --indicator ci-v100-rc3-redis.example
# On Ubuntu: kill "$(cat /tmp/rg-rc3-redis.pid)" and confirm Redis PING fails.
cat /tmp/rg-rc3-redis-token | python3 adversarial_redis_recovery_probe.py \
  --url http://192.168.122.73:18092 --stage outage \
  --indicator ci-v100-rc3-redis.example
# On Ubuntu: restart the same disposable Redis configuration and reseed the
# record, because persistence is disabled.
cat /tmp/rg-rc3-redis-token | python3 adversarial_redis_recovery_probe.py \
  --url http://192.168.122.73:18092 --stage healthy \
  --indicator ci-v100-rc3-redis.example
```

## Results and limits

| Stage | Seeded `threat_lookup` | Core `classify` | Probe verdict |
| --- | --- | --- | --- |
| Redis healthy | HTTP 200, `found=true`, `source=request_guard_lab` | HTTP 200, successful result | 2/2 |
| Redis stopped | HTTP 200, JSON-RPC `-502 UPSTREAM_ERROR` | HTTP 200, successful result | 2/2 |
| Redis restarted and reseeded | HTTP 200, `found=true`, `source=request_guard_lab` | HTTP 200, successful result | 2/2 |

The probe printed `pass=true` for both checks at all three stages; the
outage `-502` is an expected-failure pass, not a successful lookup. Before the
outage, `redis-cli PING` returned `PONG`; after the disposable Redis process
was killed, PING failed while `kill -0` confirmed the original MCP PID
remained alive. After Redis restart and reseed, PING again returned `PONG`
and that MCP PID remained alive. The MCP process was not restarted or
reconfigured. Redis downtime and time to first successful post-restart
lookup were not timed.

The MCP stdout/stderr log was nonempty (1,865 bytes). Exact-string searches
with `grep -F -q -f /tmp/rg-rc3-redis-token` and
`grep -F -q ci-v100-rc3-redis.example` found neither synthetic bearer nor
indicator in this MCP log. The token file contained one nonempty line from
`openssl rand -hex 32`. The Redis logs and Kali probe output were not
searched for these values. This MCP-log-only check is not a general leak proof.

Host load was 0.88 and I/O PSI `full avg10` was 0.00 before boot. Guests were
booted sequentially; after probes, load was 1.90 and PSI `full avg10` was
0.15. The disposable Redis and MCP processes, archive/binary copies, logs,
token files, and probe copies were removed; both guests were shut down and
verified off with `virsh -c qemu:///system list`. The Redis system service
was left inactive. These load and PSI values are point checks for host
resource contention, not performance benchmarks.

The synthetic bearer was stored in guest `/tmp` and the MCP process
environment, where privileged local processes could inspect it. Plain HTTP
was used only on the isolated lab network. This test does not cover Redis
TLS/authentication, persistence, failover, concurrent clients, or the rest
of [issue #125](https://github.com/rhamenator/request-guard-mcp/issues/125).
