# Public v0.1.5 Redis outage and recovery

On 2026-10-21 (America/Detroit), Kali `copperfin-kali-full` exercised a
seeded Redis lookup on Ubuntu `copperfin-ubuntu26-deb`. Ubuntu ran the
**published** v0.1.5 Linux x64 glibc archive; Kali ran the stdlib-only probe
pinned below. This is one bounded backend recovery cycle, not a Redis
cluster, TLS, or general availability qualification.

## Artifact and lab limits

- Tag commit: `f76ff9d2558fac705f091d9b858d3bc180b4f0bd`.
- [Public archive](https://github.com/rhamenator/request-guard-mcp/releases/download/v0.1.5/request-guard-mcp-v0.1.5-linux-x64.tar.gz)
  SHA256: `7e1b9f25719de1a2e0db8803167188de7df161d1df3c15b22bd67385320aacc0`.
  Its public `.sha256` sidecar passed `sha256sum -c` **inside Ubuntu**.
- Extracted public binary SHA256:
  `2c68a15272619d9b2240303815f4dcf61bc283eac3d022deb3227ea17711e25f`.
- Kali probe `scripts/adversarial_redis_recovery_probe.py` SHA256:
  `2933e9b532989f1a958c3be9d1d231ad3a202d19d8aba20f4042dc3a37b33c0d`;
  dependency `scripts/adversarial_probe.py` SHA256:
  `7a9a91be25a810778e510b3e573ec39cfacdc42efc70840dd11f1be6a1fb674c`.
- Kali `192.168.122.74` contacted only the owned Ubuntu MCP endpoint
  `192.168.122.73:18092` on the isolated libvirt network. Redis 8.0.5
  listened only on Ubuntu loopback `127.0.0.1:16379`; no persistence was
  enabled. The package was installed for this run; its default service was
  disabled and stopped. No firewall change was needed.
- The MCP server used a fresh synthetic 64-character bearer, 4,096-byte
  request cap, two-second header/body deadlines, 32-connection cap, and
  `MCP__REDIS__KEY_PREFIX=ci_probe`. Kali read the bearer on stdin. No real
  credentials or production indicators were used.

## Reproduction and observed results

Inside Ubuntu, verify and extract the public archive before launching the
server. Run these commands from its `/tmp` lab directory, using only a
synthetic bearer. The explicit indicator and Redis record are test data.
The `.example` suffix makes the server classify this indicator as a domain,
so it looks up the `ci_probe:threats:domain` hash:

```bash
sha256sum -c request-guard-mcp-v0.1.5-linux-x64.tar.gz.sha256
tar -xzf request-guard-mcp-v0.1.5-linux-x64.tar.gz
sha256sum request-guard-mcp-v0.1.5-linux-x64/request-guard-mcp
umask 077
openssl rand -hex 32 > /tmp/request-guard-redis-token
redis-server --bind 127.0.0.1 --port 16379 --save '' --appendonly no \
  --loglevel warning > /tmp/request-guard-redis.log 2>&1 &
echo $! > /tmp/request-guard-redis.pid
for attempt in $(seq 1 50); do
  [ "$(redis-cli -h 127.0.0.1 -p 16379 PING 2>/dev/null)" = PONG ] && break
  sleep 0.1
done
test "$(redis-cli -h 127.0.0.1 -p 16379 PING)" = PONG
redis-cli -h 127.0.0.1 -p 16379 HSET ci_probe:threats:domain \
  ci-v015-redis.example \
  '{"threat_type":"ci_probe","severity":"high","source":"request_guard_lab"}'
AUTH_TOKENS="$(cat /tmp/request-guard-redis-token)" \
MCP__HOST=192.168.122.73 MCP__PORT=18092 \
MCP__REDIS__URL=redis://127.0.0.1:16379 \
MCP__REDIS__KEY_PREFIX=ci_probe \
MCP__LIMITS__MAX_REQUEST_BYTES=4096 \
MCP__LIMITS__HTTP_HEADER_TIMEOUT_SECS=2 \
MCP__LIMITS__HTTP_BODY_TIMEOUT_SECS=2 \
MCP__LIMITS__MAX_CONNECTIONS=32 \
./request-guard-mcp-v0.1.5-linux-x64/request-guard-mcp \
  > /tmp/request-guard-redis-mcp.log 2>&1 &
echo $! > /tmp/request-guard-redis-mcp.pid
```

The run started both processes in the background and recorded their PIDs for
cleanup. Transfer the synthetic bearer file contents over authorized SSH
directly to an owner-readable file on Kali. For example, from a host with
configured SSH aliases for the two guests, use
`ssh ubuntu-lab 'cat /tmp/request-guard-redis-token' | ssh kali-lab 'umask 077; cat > /tmp/request-guard-redis-token'`
with shell `pipefail` enabled. The value should not be placed in a process
argument or committed file. From Kali's checkout, first run the healthy probe:

```bash
PRIVATE_TOKEN_FILE=/tmp/request-guard-redis-token
cat "$PRIVATE_TOKEN_FILE" | python3 scripts/adversarial_redis_recovery_probe.py \
  --url http://192.168.122.73:18092 --stage healthy \
  --indicator ci-v015-redis.example
```

On Ubuntu, stop **only** the disposable Redis process, and confirm it is
unreachable while the MCP process remains running:

```bash
kill "$(cat /tmp/request-guard-redis.pid)"
sleep 1
! redis-cli -h 127.0.0.1 -p 16379 PING >/dev/null 2>&1
```

On Kali, run the outage probe:

```bash
PRIVATE_TOKEN_FILE=/tmp/request-guard-redis-token
cat "$PRIVATE_TOKEN_FILE" | python3 scripts/adversarial_redis_recovery_probe.py \
  --url http://192.168.122.73:18092 --stage outage \
  --indicator ci-v015-redis.example
```

On Ubuntu, restart and reseed Redis because persistence was disabled:

```bash
redis-server --bind 127.0.0.1 --port 16379 --save '' --appendonly no \
  --loglevel warning > /tmp/request-guard-redis-restart.log 2>&1 &
echo $! > /tmp/request-guard-redis.pid
for attempt in $(seq 1 50); do
  [ "$(redis-cli -h 127.0.0.1 -p 16379 PING 2>/dev/null)" = PONG ] && break
  sleep 0.1
done
test "$(redis-cli -h 127.0.0.1 -p 16379 PING)" = PONG
redis-cli -h 127.0.0.1 -p 16379 HSET ci_probe:threats:domain \
  ci-v015-redis.example \
  '{"threat_type":"ci_probe","severity":"high","source":"request_guard_lab"}'
```

On Kali, run the recovery probe:

```bash
PRIVATE_TOKEN_FILE=/tmp/request-guard-redis-token
cat "$PRIVATE_TOKEN_FILE" | python3 scripts/adversarial_redis_recovery_probe.py \
  --url http://192.168.122.73:18092 --stage healthy \
  --indicator ci-v015-redis.example
```

| Stage | Seeded `threat_lookup` | Core `classify` | Probe verdict |
| --- | --- | --- | --- |
| Redis healthy | HTTP 200, `found=true`, `source=request_guard_lab` | HTTP 200, successful result | 2/2 |
| Redis stopped | HTTP 200, JSON-RPC `-502 UPSTREAM_ERROR` | HTTP 200, successful result | 2/2 |
| Redis restarted and reseeded | HTTP 200, `found=true`, `source=request_guard_lab` | HTTP 200, successful result | 2/2 |

The MCP log was nonempty and bounded at 1,865 bytes, measured with `wc -c`
on Ubuntu. Fixed-string checks (`grep -F -q -f` for the bearer file and
`grep -F -q` for the indicator)
found neither the synthetic bearer nor the synthetic indicator in it. That
is a scoped log check, not proof against all secret leakage. The two Redis
logs were not inspected for those strings. After the probe, the disposable
MCP and Redis processes, archive/binary copies, logs, and bearer files were
removed; both lab VMs were shut down. The Redis package remains installed
in Ubuntu, with its default service disabled. The existing
`copperfin-vfp9-win11` VM was untouched. Operator samples from `uptime` and
`/proc/pressure/io` showed host load 0.15 before boot and 1.37 after probes;
I/O PSI `some avg10` was 0.00 at both samples and briefly 1.19 during guest
boot. These are point observations, not workload benchmarks.

This verifies one seeded lookup, deterministic outage response, core
classification availability, and lookup recovery after reseeding. It does
not test Redis TLS/authentication, persistence, failover, multiple clients,
or the full [v1.0 release gate](https://github.com/rhamenator/request-guard-mcp/issues/125).
