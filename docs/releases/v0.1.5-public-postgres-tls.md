# Public v0.1.5 PostgreSQL TLS trust qualification

On 2026-10-21 (America/Detroit), the **published** v0.1.5 Linux x64 musl
binary was tested inside a disposable, pinned Alpine container against a
disposable PostgreSQL 18 TLS server. The packaged binary passed five
positive/negative trust cases. This extends the [separate Kali-to-Ubuntu
PostgreSQL outage test](v0.1.5-kali-ubuntu-postgres-recovery.md); this TLS
test's MCP client ran **inside** the container, not from Kali.

## Reproduction and outcome

From the repository root, download the public archive and sidecar into a
temporary directory, verify the sidecar, extract the binary, then run:

```bash
python3 scripts/smoke_alpine_postgres_tls.py \
  --binary /path/to/request-guard-mcp-v0.1.5-linux-x64-musl/request-guard-mcp \
  --expected-version 0.1.5
```

The wrapper runs the exact binary in a container with a 1 GiB memory limit,
two CPUs, 128-process limit, 256 MiB temporary filesystem, and the pinned
Alpine image. It installs `ca-certificates`, `openssl`, Python 3, and
PostgreSQL 18 **inside that container**. Those package versions are resolved
by Alpine's package repository at run time and are not pinned by this probe;
repeating the test later may exercise newer packages. Docker's default
network is used for package installation. Database and MCP endpoints remain
on container loopback; this is not a network-disconnected sandbox. The
PostgreSQL server binds loopback on port 15432 and opens a Unix socket inside
the container's temporary filesystem. The test CA and server certificate are generated
for `pgci.test`, mapped to loopback in the container. The test starts MCP on
loopback port 18780 with freshly generated synthetic bearer and cache-scope
values. No production credential or external database is involved.

The probe returned:

```text
PASS Alpine PostgreSQL TLS: explicit CA, untrusted CA, hostname, OS store, private logs
```

The wrapper requires successful `initialize`, `classify`, and
`replay_decision` for both the explicit trusted CA and OS-store trusted CA
cases with `sslmode=verify-full`.
An unrelated CA must make the server fail startup with `UnknownIssuer`; a
trusted CA with an IP address in place of the certified hostname must fail
with a name mismatch. With no explicit CA, the unmodified container OS
store must reject the private CA; after that CA is added **inside the
disposable container**, the OS store must accept it. The probe requires
nonempty, bounded MCP and PostgreSQL logs and checks both for its synthetic
bearer and cache-scope value on a successful run. The values are not sent to
PostgreSQL, so its log check is a limited safeguard; log checks are skipped
if an earlier assertion fails. Rejection assertions match specific rustls
error strings and may need updating after a legitimate library wording
change. These are scoped checks, not proof against every secret or
certificate error. The PostgreSQL cluster uses local test trust
authentication, and its short-lived server certificate uses RSA-2048 with a
DNS SAN; authenticated database connections are outside this test.

The wrapper requested container removal, and a subsequent host `docker ps`
listed no remaining test container. The operator observed Docker initially
inactive and disabled on the host, started it for this bounded test, then
returned it to an inactive service; its socket remained active. No local VM, host CA store, or
host PostgreSQL installation was changed. The host's package/image cache may
retain the pinned Alpine image and downloaded packages.

This verifies the packaged **musl** binary's PostgreSQL TLS trust and
rejection behavior in one disposable Alpine run. It does not establish a
remote or clustered database's availability, glibc/Windows/macOS TLS parity,
hostwide certificate policy, PostgreSQL outage/recovery in this TLS setup
(the imported recovery script's `main()` was not run), or the full [v1.0 release
gate](https://github.com/rhamenator/request-guard-mcp/issues/125).
