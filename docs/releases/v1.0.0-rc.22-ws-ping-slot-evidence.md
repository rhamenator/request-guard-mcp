# Unpublished rc.22 authenticated WebSocket slot retention

On 2026-10-23 UTC, a bounded loopback probe against the exact private rc.22
Linux x64 glibc binary confirmed that authenticated Ping frames can keep every
configured WebSocket permit occupied beyond the idle timeout. This is an
availability and fairness risk for callers who share a server, including
callers with distinct tokens. It is
not an authentication bypass or a production 256-connection load result.
Issue [#240](https://github.com/rhamenator/request-guard-mcp/issues/240)
tracks the decision and mitigation; general ingress fairness remains open in
[#177](https://github.com/rhamenator/request-guard-mcp/issues/177).

## Exact input and bounded method

- Draft PR #149 source head was
  `31f1c764ac5b4eef47de372827dc717da4a1094e`. The private rc.22 Linux
  x64 glibc archive SHA256 was
  `1fb92eaf4753ec641a73335aebb88f34a9ea805a8276b93fc833df851b01028b`;
  its extracted binary SHA256 was
  `962c2e19bcaa135589a5c44c357d07f4d09ffdf4f35f56ca44672ec609568636`.
  The archive sidecar was verified as part of the rc.22 candidate gate.
- `scripts/probe_ws_ping_slot_retention.py --binary <extracted-binary>` runs
  only on loopback with two fresh synthetic bearers, `MAX_CONNECTIONS=2`, a
  two-second WebSocket idle timeout and no backend. It requires optional
  Python `websockets` 15.x, used locally at 15.0.1. It prints the binary hash
  but no credential or raw server log. The bearers exist only in process
  memory/environment; the server process and temporary log are removed.
- The probe first verifies that two silent authorized WebSockets close near
  the two-second deadline, then a fresh upgrade with the second bearer
  succeeds. It opens two sockets with the first bearer, sends Ping and reads
  Pong on each every 0.5 seconds for six seconds, tries a third authorized
  upgrade with the second bearer after three seconds, checks that its 503
  body identifies the WebSocket connection cap, closes the held sockets, and
  checks a fresh authorized upgrade with the second bearer.

Observed output on the extracted binary:

```json
{"binary_sha256": "962c2e19bcaa135589a5c44c357d07f4d09ffdf4f35f56ca44672ec609568636", "silent_control_close_seconds": [2.0, 2.001], "control_recovered_upgrade": 101, "ping_clients": 2, "ping_interval_seconds": 0.5, "idle_timeout_seconds": 2, "probe_after_seconds": 3.001, "third_upgrade": 503, "third_limit_body_match": true, "third_used_distinct_token": true, "recovered_upgrade": 101, "process_alive": true}
```

This output came from the revised, checked-in script. A scoped read-only Claude
source review of `transport_ws.rs`, `server.rs`, `config.rs`, the WebSocket
probe and gate docs found that each received Ping refreshes `socket.recv()`'s
idle timer, while the WebSocket connection permit lives until the handler
returns. Authentication and Origin checks run before the upgrade and permit;
this route requires a valid token. That review did not inspect every source
file or run a binary. The runtime test supplies the two-slot observation.

This result does not prove default-capacity, distributed, production ingress
or TLS behavior. A legitimate client might send keepalive Pings for a long
session. Stable approval needs a documented fairness decision and qualified
mitigation that preserves ordinary MCP WebSocket traffic. PR #149 remains
draft and no public v1.0 asset was created by this probe.
