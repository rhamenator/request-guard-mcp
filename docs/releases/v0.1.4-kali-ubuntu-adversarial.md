# Public v0.1.4 Kali-to-Ubuntu adversarial run

On 2026-10-20 (America/Detroit), Kali Linux 2026.3 exercised the **public
v0.1.4 Linux x64 archive** installed in Ubuntu 26.04.1. The owned endpoint was
`192.168.122.73:18086` on the libvirt lab network; Kali was
`192.168.122.74`. This is runtime evidence for the published artifact, not a
claim that every deployment mode or the stable-release gate has passed.

## Artifact and scope

- Tag commit: `0cbb4e1f37fc8fdbb1ddf8440c23b97cca483cc5`.
- Public archive: `request-guard-mcp-v0.1.4-linux-x64.tar.gz`, SHA-256
  `c13e5723f9e932279dabe27563ea3a1f0ad7e8de36b3c332efa65286635b8be8`.
  Its public `.sha256` sidecar passed `sha256sum -c` inside Ubuntu.
- Extracted executable SHA-256:
  `e1863970dc8fdc96bb861af667bf7bc3f52810b2319190f8f2c192b033ab0fd5`.
- The server used a fresh synthetic 64-character bearer token, HTTP on the
  isolated libvirt network, a 4,096-byte request cap, two-second HTTP header
  and body deadlines, and a 32-connection cap. A separate listener with a
  two-connection cap served the burst probe. `MCP_ALLOWED_ORIGINS` was unset,
  so an explicit browser Origin was denied by default. No Redis, PostgreSQL,
  MaxMind, OTLP, or TLS proxy was configured in this two-VM run.
- The probes were copied from main commit `7840082` except the new
  `scripts/adversarial_transport_v014_probe.py` added with this evidence.
  Its final SHA-256 is
  `d95ddf101d74fa1e78cbd79db6cdb33d130b50c262cb47185cb544da6e633d53`.
  The public tag's [release workflow](https://github.com/rhamenator/request-guard-mcp/actions/runs/39505752906)
  independently passed five native platforms, official MCP Inspector, and
  packaged Alpine Redis/PostgreSQL outage and TLS probes. Those CI results
  are distinct from this two-VM run.

After an independent review found that status-only checks could give false
passes, the final transport script now checks exact error bodies, requires an
empty GET body and both `POST` and `GET` in `Allow`, requires a healthy ping
after rejections, and refuses non-private or redirecting target URLs. It
passed **11/11** in an isolated host loopback namespace against the same
binary digest from the v0.1.4 npm bundle. The Kali result above preceded
these assertion changes and is not represented as a final-script Kali run.

The official Inspector fresh-install matrix and real Redis/PostgreSQL
healthy-outage-recovery/TLS tests were exercised by the **exact v0.1.4 tag
workflow**, not repeated from Kali in this run. The direct lab endpoint did
not test public TLS termination or arbitrary third-party MCP clients.

## Bounded scanner capture

Kali ran Nmap 7.99 and Nikto 2.6.1 only against the Ubuntu lab port. Ubuntu
captured each run with `tcpdump -i any -s 0` and a filter for Kali and TCP
18086. Captures reported **zero kernel drops**. Host TShark 4.6.4 and the
committed `scripts/verify_scanner_capture.py` verified message boundaries and
response accounting, including payloads TShark did not decode as HTTP.

| Nmap | `timeout 70s nmap -Pn -sT -sV -p 18086 --script http-methods,http-headers --max-retries 1 --host-timeout 60s 192.168.122.73` | 30 across 30 streams | 26 | 0 | `85af3a6e48af3c817f17d494dfb4388941d4e9419087bb9c5aeb59ea47a57ec5` |
| Nikto | `timeout 20s nikto -host http://192.168.122.73:18086 -maxtime 15s -timeout 2 -nointeractive -Tuning 1234 -Pause 0.05` | 299 across 5 streams | 299 | 0 | `7786374da7d5a8788609f82ab690d0a40ba4ce866aeb0e7767a1f76087bb664a` |

Nmap saw an open port but no product/version banner; malformed service probes
received 400 and unknown paths 404. Nikto stopped at its 15-second bound with
zero transport errors. It offered four generic browser/TLS header suggestions
(`Referrer-Policy`, `Permissions-Policy`, HSTS, CSP). These are not confirmed
server defects for the documented API-behind-TLS-proxy deployment. A fresh
authenticated HTTP probe passed after both scanners. The raw captures had no
bearer token. They are retained locally, outside Git, as owner-readable files
under `dist/v0.1.4-adversarial-lab/` for independent replay of
`verify_scanner_capture.py`; they are not release assets.

## Reproduction and limits

Use a new synthetic token of at least 32 characters and an authorized lab
endpoint. Pipe it on stdin instead of putting it in command arguments or
published logs. With the server limits above, run:

```bash
cat PRIVATE_TOKEN_FILE | python3 scripts/adversarial_probe.py --url http://LAB_IP:18086 --max-request-bytes 4096
cat PRIVATE_TOKEN_FILE | python3 scripts/adversarial_ws_probe.py --host LAB_IP --port 18086 --max-request-bytes 4096
cat PRIVATE_TOKEN_FILE | python3 scripts/adversarial_transport_v014_probe.py --url http://LAB_IP:18086
cat PRIVATE_TOKEN_FILE | python3 scripts/adversarial_classifier_probe.py --url http://LAB_IP:18086
cat PRIVATE_TOKEN_FILE | python3 scripts/adversarial_envelope_fuzz_probe.py --url http://LAB_IP:18086 --cases 128
cat PRIVATE_TOKEN_FILE | python3 scripts/adversarial_slow_client_probe.py --host LAB_IP --port 18086 --max-request-bytes 4096
cat PRIVATE_TOKEN_FILE | python3 scripts/adversarial_backend_probe.py --url http://LAB_IP:18086
```

The two-slot burst probe requires a separate listener with
`MCP__LIMITS__MAX_CONNECTIONS=2`. The log and 63-second saturation probes
start their own packaged-binary subprocess on Ubuntu loopback. For scanner
counts, capture each command separately with `tcpdump -i any -s 0 -w FILE
host KALI_IP and tcp port 18086`, stop capture, confirm zero kernel drops, and
run `python3 scripts/verify_scanner_capture.py --pcap FILE --scanner nmap`
or `--scanner nikto` on the corresponding capture. Scope and time bounds for
the scanner commands are in the table above. The transport probe refuses
redirects and public or non-numeric hosts, limiting bearer-token use to a
private lab IP.

Host load averaged roughly 1-3 during the VM window; full host I/O PSI
`avg10` was 0.00 before and after the scanners. One unrelated Copperfin
Windows VM was already running and was left untouched. No firewall change
was needed. Both lab servers stopped, temporary tokens and guest captures
were deleted, and Kali/Ubuntu shut down cleanly.

No product defect was confirmed by these bounded probes. This does not prove
all classifier evasions, distributed exhaustion, cross-token persistence
isolation, or complete Streamable HTTP interoperability. Issue #59 tracks
strict transport scope. Issue #118 tracks the remaining review and promotion
decision; v0.1.4 remains experimental until those checks are reconciled. This
is one bounded run and its observations are self-reported; retained captures
allow a reviewer to independently recheck scanner counts, while the other
runtime probes require rerunning their documented commands.
