# Public v0.1.5 Kali-to-Ubuntu adversarial subset

On 2026-10-21 (America/Detroit), the Kali guest
`copperfin-kali-full` exercised the **published** v0.1.5 Linux x64 glibc
archive installed in the Ubuntu guest `copperfin-ubuntu26-deb`. The owned
libvirt endpoint was `192.168.122.73:18086`; Kali was
`192.168.122.74`. This is bounded runtime evidence, not completion of the
stable v1.0 release gate.

## Artifact and lab limits

- Tag commit: `f76ff9d2558fac705f091d9b858d3bc180b4f0bd`.
- Public archive `request-guard-mcp-v0.1.5-linux-x64.tar.gz` SHA256:
  `7e1b9f25719de1a2e0db8803167188de7df161d1df3c15b22bd67385320aacc0`.
  The public sidecar passed `sha256sum -c` **inside Ubuntu**.
- Extracted public binary SHA256:
  `2c68a15272619d9b2240303815f4dcf61bc283eac3d022deb3227ea17711e25f`.
- Ubuntu server: synthetic 64-character bearer token, plain HTTP on the
  isolated libvirt network, 4,096-byte request cap, two-second header/body
  deadlines, 32-connection cap. `MCP_ALLOWED_ORIGINS` was unset, so an
  explicit unlisted Origin was denied;
  Redis, PostgreSQL, MaxMind, OTLP, and TLS proxy were not configured.
- Kali scripts were copied from main at `fe6b0c0`, which pins their source.
  The token was passed to
  probes over stdin and was not placed in committed files or scanner
  captures. Nmap was 7.99; Nikto was 2.6.1.

## Bounded scanner capture

Kali scanned only the owned endpoint. Ubuntu captured each scanner separately
with `tcpdump -U -i any -s 0` and
`host 192.168.122.74 and tcp port 18086`. The committed
`scripts/verify_scanner_capture.py` checked message boundaries in every TCP
stream and required zero retransmissions; it uses TShark 4.6.4 and a
hardcoded Kali source IP of `192.168.122.74`. Both final captures reported
zero kernel drops. Separately,
`tshark -r CAPTURE.pcap -Y 'http.authorization' -T fields -e http.authorization`
returned no decoded HTTP authorization header in either capture. This is a
decoded-field check, not a byte-for-byte search for every possible secret.

| Scanner | Bounded command | On-wire probe messages | Decoded HTTP requests | HTTP responses | Retransmissions | Capture SHA256 |
| --- | --- | ---: | ---: | ---: | ---: | --- |
| Nmap | `timeout 70s nmap -Pn -sT -sV -p 18086 --script http-methods,http-headers --max-retries 1 --host-timeout 60s 192.168.122.73` | 30 across 30 streams | 3 | 26 | 0 | `091d7edcd3e16921b2d3627281291d0983f3f0c4e4ccf1ce24da5b663dbfcc9e` |
| Nikto | `timeout 20s nikto -host http://192.168.122.73:18086 -maxtime 15s -timeout 2 -nointeractive -Tuning 1234 -Pause 0.05` | 305 across 5 streams | 299 | 305 | 0 | `792d9e1d38bea8d456799063c656643f1fe521852589932e5273be46b7663fdb` |

The scanner-capture verifier passed on both final captures. Nmap sends
service/version probes that are not HTTP requests, explaining its 30 wire
messages versus three decoded HTTP requests. Six Nikto messages were not
decoded as HTTP requests, but the verifier checked their segment boundaries
and observed a response for every one of its 305 messages. These counts
describe this run, not a fixed scanner workload across versions or timing.

The first Nmap capture was incomplete: it had only nine captured packets
despite a larger receive count. It was discarded as request-count evidence.
The scanner was rerun with immediate packet writes (`tcpdump -U`), then the
final capture had 302/302 packets captured/received and zero dropped.
Nikto's final capture had 948/948 packets captured/received and zero
dropped. The final raw captures are retained locally outside Git under
`dist/v0.1.5-kali-ubuntu/`; they are not release assets. Nmap and Nikto
reported generic HTTP response/header observations, but no Request Guard
defect was confirmed from these unauthenticated scanner probes.

## Reproduction and limits

Use a new synthetic token of at least 32 characters on an authorized lab
endpoint. Set `PRIVATE_TOKEN_FILE` to an owner-readable file (`chmod 600`)
containing it. The server receives it in its process environment, which a
privileged local process can inspect. Bind `0.0.0.0` over plain HTTP **only**
on an isolated lab network. Start the verified Ubuntu binary with the tested
limits:

```bash
AUTH_TOKENS="$(cat "$PRIVATE_TOKEN_FILE")" MCP__HOST=0.0.0.0 MCP__PORT=18086 \
  MCP__LIMITS__MAX_REQUEST_BYTES=4096 \
  MCP__LIMITS__HTTP_HEADER_TIMEOUT_SECS=2 \
  MCP__LIMITS__HTTP_BODY_TIMEOUT_SECS=2 \
  MCP__LIMITS__MAX_CONNECTIONS=32 \
  ./request-guard-mcp-v0.1.5-linux-x64/request-guard-mcp
```

Pipe the same token to each Kali probe on stdin. Examples with the same
server limits:

```bash
cat "$PRIVATE_TOKEN_FILE" | python3 scripts/adversarial_probe.py --url http://192.168.122.73:18086 --max-request-bytes 4096
cat "$PRIVATE_TOKEN_FILE" | python3 scripts/adversarial_ws_probe.py --host 192.168.122.73 --port 18086 --max-request-bytes 4096
cat "$PRIVATE_TOKEN_FILE" | python3 scripts/adversarial_classifier_probe.py --url http://192.168.122.73:18086
cat "$PRIVATE_TOKEN_FILE" | python3 scripts/adversarial_transport_v014_probe.py --url http://192.168.122.73:18086
cat "$PRIVATE_TOKEN_FILE" | python3 scripts/adversarial_envelope_fuzz_probe.py --url http://192.168.122.73:18086 --cases 128
cat "$PRIVATE_TOKEN_FILE" | python3 scripts/adversarial_slow_client_probe.py --host 192.168.122.73 --port 18086 --max-request-bytes 4096
cat "$PRIVATE_TOKEN_FILE" | python3 scripts/adversarial_backend_probe.py --url http://192.168.122.73:18086
```

The operator sampled host load at 0.72 before booting the two guests and
1.74 after the probes; I/O PSI `some avg10` was 0.00 at both samples.
A Copperfin Windows guest
was already running and was left untouched. No firewall change was needed.
The lab server and temporary tokens were removed, and Kali/Ubuntu shut down
cleanly.

This run does not establish unknown classifier evasion resistance,
distributed exhaustion, cross-token persistence isolation, healthy
Redis/PostgreSQL outage recovery, TLS trust, or compatibility with every MCP
client. The cross-VM run did not repeat the separate connection-burst,
synthetic-log, or sustained-exhaustion probes; the exact public binary passed
those on host loopback as recorded in the linked public qualification.
The remaining cases are part of the [full adversarial release
gate](../adversarial-release-gate.md) and [v1.0 issue
#125](https://github.com/rhamenator/request-guard-mcp/issues/125).
