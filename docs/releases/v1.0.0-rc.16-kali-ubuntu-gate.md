# Private rc.16 cross-VM and PostgreSQL TLS gate

On 2026-10-23 (UTC), Kali `copperfin-kali-full` exercised the **private,
unpublished** v1.0.0-rc.16 Linux x64 glibc archive on Ubuntu
`copperfin-ubuntu26-deb`. A separate disposable Alpine container exercised
the matching private musl archive's PostgreSQL TLS trust behavior. This is a
bounded candidate replay, not approval to publish stable v1.0.

The PostgreSQL test created database `request_guard_rc16_lab` under peer
authentication and stopped/restarted the existing PostgreSQL 18 cluster. It
restored that cluster online and removed the disposable database. The
disposable Redis process had persistence disabled and was stopped after the
test. The temporary server processes, copied archives, scripts and synthetic
secret files were removed. The preexistence of the `copperfin` PostgreSQL
role was not recorded, so the run did not delete that role; the guest disk was
retained and may still contain it.

The MCP logs were nonempty (core 10,841 bytes, PostgreSQL 2,139 bytes,
Redis 1,835 bytes). Exact-string searches found neither synthetic bearer,
HMAC nor seeded indicator in those **MCP logs**. Encoded or truncated forms
were not searched. This did not search the PostgreSQL or Redis logs or prove
absence of all possible secret leakage.
Both lab guests were shut down and verified off; the preexisting Copperfin
Windows guest was left untouched. Host I/O PSI `full avg10` was 0.00 before
boot and again after the backend probes; it briefly reached 1.58 during
staggered guest startup. A point sample after the Alpine test was 0.65;
these samples do not establish absence of host pressure throughout the
runs. No firewall change was made.

## PostgreSQL TLS trust and limits

`scripts/smoke_alpine_postgres_tls.py` ran the exact extracted private musl
binary in the pinned Alpine 3.24.2 image
`sha256:294b683cb724975bec92580e1e685676bd4b50bda910ddb8c51d4cabeaec77e6`.
It passed explicit trusted CA, untrusted CA rejection, hostname mismatch,
unmodified OS-store rejection, and OS-store trust after installing the test
CA **inside the disposable container**, plus an exact-string check for its
synthetic secrets in nonempty MCP and PostgreSQL logs, each at most 64 KiB.
The test database and MCP server used container loopback. Alpine packages
were resolved live at test time and their exact versions were not recorded;
only the base image was pinned. The container used Docker networking
for package installation. No host or guest CA store was changed. The test
container was removed and Docker was returned to its initially inactive
service state.

The cross-VM backend and adversarial checks exercised glibc only; TLS trust
was exercised on musl only. This does not prove glibc or other-platform TLS
parity, production TLS termination, remote database failover,
Redis TLS, distributed ingress fairness, scanner capture counts, all-client
compatibility, or a 256-client deployment. No public v1 tag, release, GHCR
image, npm package, or Agensi ZIP was created. Final adversarial LLM review,
owner approval and approved-tag public artifact verification remain in
[issue #125](https://github.com/rhamenator/request-guard-mcp/issues/125).
