## Kali-to-Ubuntu packaged-binary test

The extracted **same Linux binary** ran inside `copperfin-ubuntu26-deb`
(`192.168.122.73`); `copperfin-kali-full` (`192.168.122.74`) sent real TCP
requests. The first server used a synthetic 64-character bearer token,
4,096-byte request cap, one-second header/body deadlines, and no optional
backend. Kali ran the committed stdlib HTTP, WebSocket, classifier, slow-client,
and malformed-envelope probes against TCP 18086:

```bash
cat /tmp/lab/token | python3 adversarial_probe.py \
  --url http://192.168.122.73:18086 --max-request-bytes 4096
cat /tmp/lab/token | python3 adversarial_ws_probe.py \
  --host 192.168.122.73 --port 18086 --max-request-bytes 4096
cat /tmp/lab/token | python3 adversarial_classifier_probe.py \
  --url http://192.168.122.73:18086
cat /tmp/lab/token | python3 adversarial_slow_client_probe.py \
  --host 192.168.122.73 --port 18086 --max-request-bytes 4096
cat /tmp/lab/token | python3 adversarial_envelope_fuzz_probe.py \
  --url http://192.168.122.73:18086 --cases 128
```

| Probe | Result |
| --- | --- |
| HTTP auth, JSON-RPC, size limits, injection as data | 10/10 passed |
| WebSocket auth, frames, MCP calls and recovery | 11/11 passed |
| Classifier evasion corpus | 19/19 passed |
| Slow headers/body and recovery | 4/4 passed |
| Deterministic malformed envelopes | 128/128 structured responses and recovery |

A second server used PostgreSQL 18 in the Ubuntu guest on TCP 18091.
Kali's `adversarial_postgres_probe.py` passed 3/3 before database stop,
3/3 during the outage (`-502 UPSTREAM_ERROR` for the dependent tools, while
MCP `ping` remained healthy), and 3/3 after restart. During the outage,
32 unauthenticated `/health` requests with eight workers all returned HTTP
200 and an `unhealthy` body; maximum observed latency was 29.66 ms. This
covers a stopped backend, not a backend that accepts connections but stalls.
The PostgreSQL probe used `--url http://192.168.122.73:18091
--request-id v012-packaged-lab-001` with `--stage healthy`, then `outage`,
then `healthy`; each invocation read the synthetic token from stdin. Ubuntu
used `pg_ctlcluster 18 main stop/start` between stages.

A separate two-slot listener on TCP 18086 shed 128/128 excess Kali
connections with no exceptions (maximum observed connect/close latency
1.19 ms) and recovered after the held sockets were released. The packaged
binary passed the synthetic-secret log probe 3/3 in Ubuntu: rejected auth
and successful classification were observed, but neither the synthetic token
nor request marker appeared in a bounded debug log capture.
The excess-connection command used `adversarial_connection_burst_probe.py
--host 192.168.122.73 --port 18086 --attempts 128` with the token on stdin.

Kali ran Nmap 7.99 and Nikto 2.6.1 only against Ubuntu TCP 18091. A full
payload capture on `virbr0` reported zero kernel drops and zero TCP
retransmissions. `verify_scanner_capture.py` verified message boundaries:
Nmap sent **30** payload-bearing probes across 30 streams, with 3 decoded
HTTP requests and 26 responses; Nikto sent **303** request payloads across
5 streams, with 297 decoded HTTP requests and 303 responses. Nikto used a
15-second maximum, so its count is expected to differ from earlier runs.
Its four suggested browser/TLS response headers are deployment advice, not
a confirmed API defect behind the documented TLS proxy.
The bounded Kali commands were `nmap -Pn -sT -sV -p 18091 --script
http-methods,http-headers --max-retries 1 --host-timeout 60s
192.168.122.73` and `nikto -host http://192.168.122.73:18091
-maxtime 15s -timeout 2 -nointeractive -Tuning 1234 -Pause 0.05`.

Host full I/O PSI was near zero before the run, briefly reached 0.87% while
both guests booted, and was 0.00% after the probes. No VM remained running
at cleanup. The synthetic token, guest processes and test files, temporary
PostgreSQL database/role, and raw packet captures were removed. OpenSnitch's
host-side temporary executable rule was removed after the fresh Inspector
smoke; no persistent rule was added for the VM tests.

## Review reconciliation and remaining gates

Claude Code independently read the auth, transport, resource-limit, backend
health, and release-workflow paths. It found no verified exploitable auth or
protocol defect in those files. Its verified release-process findings led to
tag/Cargo-version/main-ancestry validation and a packaged server-version
assertion in PR #80. It noted that the existing Inspector smoke already
rejects a missing bearer token. Its proposed stalled-backend health-check
exhaustion remains a hypothesis: the stopped-backend probe above returned
quickly, but did not simulate a blackholed backend. Claude did not inspect
the classifier engines; the runtime corpus above covers selected evasions.
Codex review threads on PR #80 were clear, and its required checks passed.

The exact **final** v0.1.2 tag will produce new archives. They must pass
the release workflow and be checked after publication; do not represent this
candidate hash as the final artifact. Build the npm package only from those
final assets, then perform a clean install and MCP client smoke before npm
publication. The Agensi skill ZIP must be built from the verified final tag
and kept local only. This evidence does not prove all MCP clients, a hung
backend, HTTP/2 rapid reset, arbitrary classifier obfuscation, or unlimited
resource-exhaustion resistance. Alpine host support remains issue #54 for
the subsequent release.
